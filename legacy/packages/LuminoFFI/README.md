# FFI

## FAQ

### なぜ struct のメモリ確保に一貫性が無いのか？

- 数学系や小規模なものは各言語バインディング側で確保している。
- それ以外は C++ 側で確保している。

これは今のところ、今後の拡張で、メンバの増減が発生しやすいかどうかを考慮している。

バイトサイズを一致させる必要があるが、言語バインダ側との齟齬の発生が怖い。
でなければ C++ 側から構造体のサイズを返す必要があるが、面倒。


### なぜ SharedLib(.dll) と StaticLib(.lib) 両方用意しているのか？

最初は LuminoEngine.lib に含めて、 LuminoFFI.dll は その lib に定義された関数を export しようとしました。
しかし、

- lib 内の関数を dll として export するには型定義ファイルなど追加の設定が必要。
- windows 以外でも、デフォルトではそのような export はされず、追加の設定が必要。

ということがあり、設定が煩雑になるのは避けたかったため、関数は dll 内で定義するようにしました。

また dll だけだと次のような問題がありました。

- テストを書くとき、SharedLibrary だと Lumino のインスタンスがわかれてしまうためコーディングミスが多くなる。またこの動作はイメージし辛くデバッグが難しくなる。
- cmake が exe と dll の依存関係を自動で組んでくれないためか、dll 側をビルドしても exe まで再リンクしてくれない。多分リンクlibに変更があればリンクしてくれるけど、この動作もわかりづらくデバッグし辛い。
